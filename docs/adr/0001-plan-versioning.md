# ADR 0001: Plan versioning

Status: Accepted
Date: 2026-10-25

## Context

Subscriptions and invoices will reference plans. Changing a plan's price or billing terms must not
rewrite the history of anything that already refers to it.

## Decisions

### Versioned vs in-place changes

`Plan::Versioning` is the only path for editing a plan.

- Changing `amount`, `interval`, `per_quantity` or `metric` creates a new plan row with
  `version + 1` and `previous_plan_id` pointing at the old row. The old row is archived.
- Changing only `name` updates the row in place.
- Any other attribute in params (`archived`, `version`, `previous_plan_id`, `organization_id`,
  `lineage_key`, ...) is rejected. The service is the domain boundary and does not rely on the
  caller's strong params.

**Name edits are a product decision:** because a rename doesn't create a version, existing
subscriptions and past invoices that reference the plan will show the new name. If invoices
ever need the name as it was at billing time, they must snapshot it rather than read it from the plan.

### Lineage key

Every version of a plan shares one `lineage_key` (UUID), generated by the database when the first
version is created and copied to each new version.

- The model marks it `attr_readonly`, so it can't be changed after creation.
- The database enforces that a version shares its predecessor's key with a composite foreign key
  `(previous_plan_id, lineage_key) → plans (id, lineage_key)`.
- The same technique enforces that a version stays in its predecessor's organization:
  `(previous_plan_id, organization_id) → plans (id, organization_id)`.

**No backfill:** the column's `gen_random_uuid()` default gives every *existing* row its own key, which
would break existing v1 → v2 chains. The `plans` table had no records when the column was added, so the
migration has no backfill. Adding a column like this to a table that already holds version chains needs
one: each row must get its chain root's key before the composite foreign keys are added.

### Concurrency

The service locks the plan row (`SELECT ... FOR UPDATE`) for the whole operation and re-checks
`archived` after locking, so concurrent edits are serialized and only one new version is created.
The unique index on `previous_plan_id` is the database backstop.

### Error contract

`execute` returns the current version of the plan (the new row when a version was created, otherwise
the same row). Failures raise subclasses of `ApplicationError`:

- `InvalidRecordError`: bad params (validation failures or non-editable attributes); `error.record`
  carries the errors. Validation runs before anything is written, so versioned and in-place changes
  fail the same way.
- `ConflictError`: the plan is archived, or the `previous_plan_id` unique index fired because the plan
  was already versioned.
